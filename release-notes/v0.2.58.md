# v0.2.58：专家席从「只审」到「动手」—— 能力早已存在，缺的是授权与追责

**一句话**：用户要求「团队角色不仅审查方案还要做方案落地执行」。落点不是"加一席执行专家"，而是**把已经存在却无人知晓的写权限变成显式契约**，并补上它暴露出的三处结构性缺口（改动归属为零、同树并发可静默覆盖、插件自路由无鉴权）。

## 1. 缘起：能力是一个省 token 开关的副作用

排查发现需求在**权限层早已满足**，只是没人知道：

| 位置 | 事实 |
|---|---|
| `src/members.ts` `nodeToolRestriction` | `skill_delivery !== 'direct'` 时**只发 `deny`、不发 `allow`** |
| 宿主语义（`dsh-tools` `ToolRestriction.allow`） | 「不传 allow = 不做可见性过滤，其余全部移除」⇒ 不传就是不滤 |
| 后果 | relay 模式下专家**继承主持人近乎全量工具面**，含 `dev_*` 注入器（等价任意代码执行） |
| 28 条 role（`experts.yaml`） | **无一**授权"动手改工作区"；`impl` 明写「只回答…不评价设计品味」、`rollout` 明写「只把结论排成可执行时间线」 |
| `src/charter.ts` | 反而下了反向命令「只做本职，严禁越权代管他人的工作」 |

⇒ 两套真相：**机制说可以写、文案说本职不许**。这不是"能力缺失"，是"授权缺失 + 追责缺失"。

## 2. 修法（六项，用户批准后全做）

```
P6 工具面单一真源   allow 恒下发；写权限不再由 skill_delivery 派生
P3 执行协议文案     charter 条件式执行段 + usage 第 20 条
P5 归属留痕         计划项 files 文件面 + 同波次重叠检测
P4′ 边界可核        boundary_notDoing 进 PlanContext（派单时即可见那面墙）
T3 RPC 鉴权         插件自注册路由复用宿主 BrowserAuth
P1 生效链           重建 lib + 同步 profile 装载副本
```

### P6：写权限从「副作用」变「契约」

- `allow` 白名单**所有模式恒下发**；`skill_delivery` 只决定 `skill` 加载器是否留给专家（relay = 正文由主持人中转，专家自取等于绕过中转）。
- 同时**收窄非执行面**：`dev_*`（运行时注入任意插件）/ `nav_*` / `present` 进 deny。
- ⚠ **执行面刻意保留**（`write`/`edit`/`pwsh`/`bash`）——收掉 shell 等于把用户需求本身挡掉。
- 新增 `restrictionDiagnostics()`：allow 被滤空（宿主改名而清单未同步）= 无工具可用的**残废席位**，`spawnNode` 把它升级成**显式报错**而非静默产出。

### P3：执行协议（条件注入）

`charter.ts` 新增「一之三、执行协议」段，**仅当 `boundary.notDoing` 非空时出现**：

- 为什么条件式：本段内容全部建立在"有一面不许动的墙"之上。无边界声明的会议挂上它，等于把「未声明边界即允许写」这个最危险的默认值写进 persona。
- 关键一条：**改完必须重建并同步产物，否则视为未生效** —— 直接针对本仓"改了 src 却没重建"的静默漂移。

### P5：同波次文件重叠（本组最重的信号）

同树并发下"两席在同一波次碰同一文件"是唯一会让改动**静默消失**的形态：后写覆盖先写、树里不留冲突标记，而宿主唯一做「每轮改动清单」的插件对 `origin === 'subagent'` **一律返回 undefined**（子代理被主动排除）⇒ 事后无从发现。

- `RoundPlanItem.files` + `collectWaveFileOverlaps()`；`round_signals` 报 `files_items` / `files_unspecified` / `file_overlaps`。
- **只呈现不判定**：不做路径规范化/glob 展开（猜出来的"等价路径"会造假红）；同一波次才算并发，跨波次已被 `depends_on` 串行。

### T3：插件自注册路由的鉴权缺口

实测（同一进程、同一端口）：

| 请求 | 改动前 | 改动后 |
|---|---|---|
| 宿主 `GET /` 无凭据 | 401 | 401 |
| 插件 RPC `POST` 无凭据 | **200 `ok:true`** | **401** |
| 插件 `GET /state` 无凭据 | 200（含全部 transcript） | **401** |

风险不在"外部攻击者"（宿主只监听 `127.0.0.1`），而在**在场的专家节点**：它持 `pwsh`，一条本机 HTTP 请求即可调 `user-actions.append` 伪造「用户要求增删专家」，而主持人下一轮**会照单执行** —— 借主持人的手改会议本身。

- 修法：**复用宿主 BrowserAuth**（`connection.requestRejection`），不自造共享密钥（避免与宿主鉴权真源分叉成两套）。
- 失败方向：宿主 connection 缺席时落回**回环兜底**，实现抛错时**判拒** —— 绝不因缺件而放行。
- 配套：客户端 `credentials: 'same-origin'`（否则同源 cookie 不发、UI 全线 401）。

## 4. ⚠ 诚实标注：过程中被推翻的判断

- 我最初判断「`ctx.subprocess` 服务不存在」——**错**，搜错了目录：它在宿主装配树而非插件 `node_modules`。由独立仲裁席指出，我实测复核后撤回。
- 我最初判断「删 `.imported` 的幽灵键即可修复预设加载」——**错**：`dsh-settings` 只在 `settings.yaml` 存在时才读 `.imported`，而该文件已被重命名 ⇒ 改它**不触发任何重放**。由仲裁席指出并采纳。
- 我最初判断「归属留痕可缓（选了串行就不必）」——**错**：串行只改变"谁写的"确定度，不产生任何归属记录，两者不可替代。
- 我最初的 T3 验证夹具用 PowerShell 发请求，**误报 401**（未传对 `Host`/`Cookie`）；改用 Node HTTP 客户端才得到可信结论。**不采信"第一次看起来对"的结果**。
