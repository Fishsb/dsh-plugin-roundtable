# RoundTable v0.2.42

**R-D「调度面」批次**：修的是用户实测反馈的两条主持人模式逻辑缺陷 —— 它们的**根因是同一个**：会议轮次只有**执行面**（自由文本派单），没有**候选面**（可选谁）与**计划面**（谁做什么、谁等谁）。

> 用户原话：「会议启用的时候调用了哪几个专家，后续所有轮次就只有这几个专家」「主持人不会根据团队成员反馈去选择更合适的成员」「接到任务下发的时候直接全部下发，好像并没有对哪些可以并行哪些可以串行做分析」。

---

## 0. 诊断（先说清毛病在哪一层，避免又去改提示词）

| 抱怨 | 证据（改前） | 根因 |
| --- | --- | --- |
| 专家名单固化 | `roundtable_status` 只回在场节点（`nodes[]`），盘中无任何候选池字段；`roundtable_list_presets` 在 usage 里只被描述为**建会前**的动作 | 每轮唯一一次信息拉取里**没有替代项**，主持人结构上无从换人 |
| 一把抓、无并行/串行 | `roundtable_next_round` 只是 `round++`；派单是自由文本；静默判据只看"派了没回" | **没有"本轮计划"这个数据结构**，依赖关系不可表达、不落账 |

两者叠加的实况：轮 0 定名册 → 轮 N 还是这批人；十个人发同一条无依赖任务，机器**照绿**。

**关键判断**：提示词层已经饱和（规则 5 早写了"每轮查册"），缺的是**信息面**与**账本面** —— 所以本批不加劝告，加数据结构。

## 1. 候选面：专家库进每轮信息面（W1）

- `roundtable_status` 新增 `talent_pool`：`total` + 逐条 `{id, name, 路由, on_stage}`。
- **刻意只给 id/name/路由，不给 role 全文**：本机实测 28 条预设、正文合计约 3.4k token，每轮灌一遍是纯浪费；要正文走 `roundtable_list_presets filter=<关键词>`，把"实时查库"变成有成本意识的动作。
- `MeetingNode` 新增 `presetId`（`add_node.preset` 解析成功时记录）：候选池的 `on_stage` 由此**精确关联**，而不是拿 role 文本比对去猜；临时写的角色留空、不算任何预设的在场席。
- 拉人不再是建会期的一次性动作：`add_node` 描述、usage 规则 3/5 都写明**会议中途按需拉席**是预期行为。
- **隔离**：`talent_pool` 只给主持人（单线制下它是"别处还有谁"的泄露面）。

## 2. 计划面：并行/串行变成必须有的一张图（W2）

`roundtable_next_round` 新增 `plan`：`[{id, task, owner, depends_on}]`。

- **语义即判据**：`depends_on` 为空 ⇒ 与同为空的项**同波并行**；非空 ⇒ 波次 = `1 + max(依赖波次)`（真串行）。
- **校验必拒**（不是警告）：依赖**成环**、`depends_on` **悬挂引用**、**未知席/已移除席**、`new:<预设>` **解析不到**、空计划。报错给出可读链与可用清单。
- **硬门（用户拍板）**：在场席 **≥2** 且没交计划 ⇒ **拒绝推进轮次**；单席免（那时不存在并行/串行这个问题）。判据抽成 `requiresDispatchPlan()`，同一函数同时被工具与夹具消费 —— 避免"文案说要交、工具其实不查"。
- **先校验、后推进**：非法计划不得烧掉一轮（否则报错本身变成预算泄漏）。
- 计划落账 `meeting.roundPlans`（保留 50 轮），`owner: "new:<预设>"` 的项进 `gaps`，明确要求先 `add_node` 再派该波。
- 返回值直接给 `waves`（立刻并发 / 等上一波）与 `gaps`。

## 3. 对账面：计划说了发给谁 vs 实际发给谁（W3）

`roundtable_status` 新增 `round_signals`：

- `plan_recorded`（本轮**是否做过调度分析**，缺计划显式报出，不静默）；
- `planned_waves` / `undispatched_owners` / `unplanned_dispatches` —— 一份"声明了却不执行"的计划**在账本上可见**；
- `pending_seats`（本轮尚未发言的在场席）；
- `out_of_scope` —— 把专家 persona 里的 `[越界转派]：<事项> | 建议承接：<职责>` **结构化提取**（改前只是文案，机器读不到，于是"这活该别人接"永远沉在发言里）。容忍全角/半角与标签缺失；没有该行**不得误报**。

导出物同步：新增「调度计划」段（逐轮逐波），并单列**「未记录调度计划的已派发轮次」** —— 否则一份一把抓的会议记录看起来与逐波派发完全一样。

## 4. 顺带修掉的一处真隔离漏洞

`roundtable_status` 的 `silence` 判据**原样返回全员席位名**：单线制（orchestrated/redteam）下节点调一次 status 就能读到同伴 key —— 与 `members.ts` 里"deny `roundtable_summarize`"要防的假隔离**同型**（文案说不认识、工具一查全认识）。

修法：非全量视角（`vis.full === false`）下 `silentSeats`/`lateReplies` 只保留 viewer **自己**那一条，`emptyRounds` 置空；主持人不受影响。`test/silence.test.mjs` 的接线守卫已扩到钉死这一步。

## 5. 提示词（只在结构就位后才改）

- 规则 3：明确 **"one node at a time" 是信息隔离，不是串行执行** —— 独立工作项应当一起下发。原文三处重复这句、写在"怎么派单"的语境里，会被读成调度指令。
- 规则 5：把 `talent_pool` 与 `round_signals` 写成**必须真的用**的两个字段（含"越界转派必须重派或并入汇总，不得丢弃"）。
- 新增规则 16「DISPATCH ANALYSIS IS STRUCTURAL」：计划语义、硬门、先拉缺口席再派该波、以及"声明不执行在账本上可见"。

## 8. 运行态实测（不接受夹具绿当达成）

在一场真会议（`orchestrated`，两个**真预设席位** verify / accept，temp 会议，验完即删）上逐条实测：

| 项 | 实测结果 |
| --- | --- |
| 候选池进信息面 | `talent_pool` 列出 **28** 条（与磁盘 `settings.yaml` 逐条计数、与 `preset-index.md` 直出表一致），两个在场席标 `ON STAGE` |
| 预设来源落账 | `meeting.json` 出现 `"presetId": "verify"` / `"accept"`；`add_node` 回执写明 `from preset verify` |
| 硬门 | 2 席不带 plan 调 `next_round` → **报错**，且 `round` / `usedRounds` 实测仍为 **0**（非法计划不烧轮） |
| 波次 | `plan=[a1→verify, a2→new:accept, a3←a1]` → `[a1, a2] → [a3]`，缺口提示 `new:accept — already on stage` |
| 缺口 | `new:` 指向的预设已在场时给出 `already on stage`（不再要求重复拉人） |
| 工作项追踪门 | 传计划外 id `zz9` → 报错并列出本轮计划项（`this round plans: a1, a2, a3`） |
| 三态对账 | 席位收到过派发但消息没打标签 ⇒ 报 **untracked（不可核，非失败）**；该席当轮什么都没收到 ⇒ 才报 **never dispatched** |
| 导出物 | 「调度计划」段逐轮逐波渲染，roster 标注预设来源 |

**运行态抓到并当场修掉的两条真缺陷**（夹具没覆盖，是实测逼出来的）：

1. **假转派**：主持人在派单里写「请在末尾写一行 [越界转派]（无则写"无"）」被旧判据（行内 `indexOf`）当成 **2 条真实转派** —— 真信号被假信号淹没。
   修法：标记必须是**行首**（容忍列表符号/前导空白），且默认排除主持人/汇聚网关发言（它们只是在转述协议）。
2. **对账口径漏洞**：a1/a3 同归 verify 时，只派 a1 而席位口径全绿 —— "同席位漏项"逃过对账。
   修法：`send_message` 增可选 `work_item`，并**只认本轮计划里真有的 id**（追踪不得可编造）；对账升级为**三态**（tracked / untracked / never dispatched），不把"不可核"说成"没做"。

第三条由专家席当场以 `[越界转派]` 提出并被采纳：`lib/index.js` mtime 早于源码改动 —— 本批收尾已重建并复验产物含最新接线。
