# RoundTable v0.2.50

**可见性修复版**：v0.2.49 之后又发现一处「状态变了但用户看不见」的问题 —— 打开「圆桌会议」Tab 就会把本会话置入讨论模式，而**空状态那一屏**（还没有会议时）此前**没有任何徽章**；恰恰是这一屏的输入框会把模式再置上一条**切走 Tab 也不关**的记录。本版补上这块可见性，并把徽章收敛成单一共享组件。

---

## 1. 用户问的那个问题，答案是「会」，而且后果不可见

用户问：**「tab 的输入框会默认启用圆桌会议讨论吗」**

答案分层如下（都经过实测，不是读注释）：

| 触发动作 | 写入的是哪一份 | 切走 Tab 后 |
|---|---|---|
| 打开「圆桌会议」Tab | `auto` | **自动撤销** |
| 敲 `/roundtable` | `manual` | **仍然开启** |
| 在空状态那一屏的输入框里打字 | `manual`（走 `roundtable/steer`） | **仍然开启** |
| 在群聊窗口的输入框里打字 | 不写模式 | —— |

会话的模式是两份独立状态的**或**：`isActive = auto || manual`（`src/mode.ts`）。

### 1.1 实测出来的不对称

用**假会话 id** 直接打 RPC，逐档录制 `mode.get` 回值：

```
auto=true              → { active: true,  manual: false }
auto=true → manual=true（steer）
        → auto=false（切走 Tab）
                       → { active: true,  manual: true }   ← 模式仍然开着
```

对照：只开 Tab 再关 Tab（不碰输入框）→ `{ active: false, manual: false }`。

**差别就是那一下打字。** 用户"只是在这一屏打了个字试试"，之后回到聊天窗口，发的每条消息都会被当成圆桌议题处理 —— 而**清掉 `manual` 只有两条路**：`/roundtable off`，或重启进程。

### 1.2 那为什么之前看不见

徽章本来就有，但只在 `RoundTableView.tsx` 的**有会议时的头部**渲染（`if (meeting === undefined) { ... }` 早退体**之后**）。空状态那一屏正好在那个早退体**里面** —— 于是恰好在最需要它的那一屏，它不存在。

而 `modeState` 这个数据**在早退之前就拿到了**（挂载时 `mode.set` 的回包 + 每 5 秒一次的 `mode.get` 轮询），不是"拿不到"。

## 2. 修法（用户从三个处置里选了 B）

审查给出了三个处置：

- **A**：把输入框的 steer 改成只置 `auto`（改模式语义，影响命令之外的行为）
- **B**：保留 `manual` 的语义，**但在空状态那一屏也显示徽章** ← 用户选了这个
- **C**：不改代码，只写文档

选 B 的理由（用户原话）：*「用户能看见状态，就不会被『看不见的开关』坑；改动小、不动模式语义」*。

**为什么不动语义是对的**：「切走 Tab 仍开启」在这个场景下并不是 bug —— 用户在圆桌会议的屏里说了一句话，期望后续消息继续按圆桌处理是合理的；真正的问题是**这个状态没有被告知**。

## 3. 抽成单一组件：`src/client/ModeBadge.tsx`

同一枚徽章要在两处出现（有会议的头部、无会议的空状态屏）。两份拷贝会立刻漂移，而它承载的是一条**状态事实** —— 两处说法不一致时，用户不知道该信哪个。

因此标记、文案、显示条件只定义一次（与 `ChatComposer` 同一理由，见 v0.2.48）。视图侧现在只有两行 `<ModeBadge state={modeState} t={translate} />`。

组件同时承担「**不画假状态**」的职责：`state === null`（真值还没问到）时**什么都不渲染** —— 先画一个"关"再跳成"开"，用户会看到一次不存在的状态变化。

## 4. 一个假标签：`（命令开启）` → `（切走 tab 仍开启）`

`manual` 现在有**两个**写入点：`/roundtable` 命令（`src/mode.ts`）**与**空状态输入框（`src/rpc.ts` 的 `steer`）。

原先子标签写的是 `（命令开启）` —— 用户在输入框里打了一句话，徽章却断言他敲过命令。这是**假标签**，不是措辞问题。

改成描述**后果**（`切走 tab 仍开启` / `(stays on after you leave)`）后，对两个来源都成立，而且正是用户此刻需要知道的事。语言键 `modeViaCommand` 随之改名为 `modePersistent`。

## 5. 验证（实测证据）

- `npm test`：**314 通过 / 0 失败**（v0.2.49 为 310）
- `node test/mutate.mjs 1..29`：**29/29 PASS，且每条都命中自己的期望守卫文案**（v0.2.49 为 27）
- `tsc` host + client **双端 0 错**

### 5.1 新增变异探针（都实证过"真的转红"）

| 编号 | 把实现改成 | 守卫转红于 |
|---|---|---|
| 28 | 空状态那一屏不画徽章 | 接线守卫⑥ `空状态那一屏没有徽章` |
| 29 | `state === null` 时照画（`if (false) return null`） | 接线守卫⑥ `真值未到前不得画徽章` |

### 5.2 新增渲染面测试 `test/mode-badge-render.test.mjs`

正则守卫只能证明"代码里写了 `<ModeBadge `"，证明不了它**真的渲得出内容**，更证明不了 `null` 档**真的什么都不画**（分支可以写得很像）。本文件把生产组件的 `ModeBadge` 真渲染成 HTML 再断言：

- 开启 → `LABEL_ON` + `data-rt-mode="on"` + title 提示；且**不含**「关」文案
- 关闭 → `LABEL_OFF` + `data-rt-mode="off"`；且**不含**「开」文案
- `null` → **渲染结果为空串**（不画假状态）
- `manual` 那一份带子标签，`auto` 那一份不带（两种来源一眼可分）

### 5.3 一处守卫是**修正**而非新增

给空状态那一屏补断言时，第一版写的是**整文件**断言：

```js
assert.match(view, /<ModeBadge state=\{modeState\}/, '空状态那一屏没有渲染共享徽章')
```

**实测（模拟变异 28，把空状态那一处换成 `<span />`）**：

```
变异后视图里还剩几处 <ModeBadge ? 1
【整文件】断言仍绿吗?  true   ← 假绿：头部那一处把空状态那处冒充了
```

即：删掉空状态那一屏的徽章，这条断言**照样绿** —— 它证明的只是"文件里某个地方有徽章"。

同一轮还试过另一种错法（用 `if (meeting === undefined) {` 的**前半段**切片）：

```
【前半段切片】含 <ModeBadge 吗?  false   ← 恒红：两处徽章都在该行之后
```

两处徽章都在早退体**内部/之后**，所以任何以该行为右边界的切片都不可能含它们。**恒红比假绿好抓，但它同样不是判据** —— 它会为一次正确的改动永久报错。

**修法**：改用早退体的**结束锚点** `const modeLabel =` 切分（与 `chat-view.test.mjs` 同一对锚点），分别断言空状态块与头部各含徽章。修正后同一变异：

```
【修正后·空状态切片】仍绿吗?  false   ← 期望 false（守卫真的转红）
```

变异 28 由此成为这条守卫的实证（它验证的是**修正后**的形状；对 v0.2.49 那份内联代码不适用，那时锚点字符串根本不存在，探针会以 `exit 3` 拒绝运行）。

## 6. 未做（明说）

- **默认视图仍是拓扑**：用户明确保留该默认值（v0.2.49 已记）。
- **`manual` 仍没有过期机制**：只能靠 `/roundtable off` 或重启清除。本版只补可见性，不改生命周期 —— 若要"闲置 N 分钟后自动关"，那是另一个改动（需要 host 侧定时器与用户拍板）。
- **RPC 路由无 origin/鉴权**：与本仓既有端点同构，非本版新引入。
