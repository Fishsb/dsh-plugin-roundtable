## 8. 追加修复：`usage.get` 对真实会议回**空 400**（真因三层，全部非类型错误）

上线自检时才发现的缺陷：带**真实** meetingId 时该端点返回 `HTTP 400 / 0 字节`，不带 payload 反而有正常报文 —— 看起来像"端点时好时坏"，实际是**它从未工作过**。三层真因，`tsc` 与既有单测都看不见：

| 层 | 错法 | 真因 |
| --- | --- | --- |
| 服务读法 | `(ctx as …).sessionProjections` 属性读 | 未在 `inject` 声明时抛 `cannot get property "sessionProjections" without inject`；该异常在 `dispatch` 的 try **之外** → 宿主只能回空 400 |
| 快照形状 | `snap.tokenUsage` | 读面是 `{ asOfSeq, values }`，应为 `snap.values.tokenUsage` |
| 字段名 | `totals.*` / 客户端读 `totalTokens` | `TokenUsageProjection` 只有四个互斥桶，**没有** `totals` 层、**没有** `totalTokens`；客户端据此只能渲染"—" |

处置：
1. **取数逻辑抽出** `src/usage.ts`（`pickProviderTokens` / `providerTokensOfSnapshot` / `providerUsageTotal`）—— 形状知识单源、夹具可断言；缺字段时返回 `undefined`（不可用），**不编造 0**。
2. **服务改 `ctx.get('sessionProjections')`**（"可用则取、不可用则 undefined"），`projections_available` 据实上报。
3. **路由回包加固**：`send()` 改为**先 `JSON.stringify` 再 `writeHead`**，序列化失败 → 可读报文而非空 400；`dispatchRpc` 调用再包一层兜底。
4. 新增 `test/usage.test.mjs`（现 **16 条**，§8+§9 共用）：12 条夹具（真形状 / 历史错形状必须取不到 / 缺失≠0 / 宿主初值四桶 0 照实回传 / 真实活会话采样 / 两套词汇不得交叉 / 未知字段与 NaN 被滤 / 合计同源 / 耗时三态与身份门）+ 4 条源码护栏（服务读法、取数走 usage.ts、先序列化、客户端不读 `totalTokens`）。
   **变异验证**：把护栏正则喂给修复前的原文 → 全部命中（会转红）；喂给修复后的文本 → 全部不命中；护栏③另证旧 `send()` 无该守卫。

**三层真因的第一方证据**（`@deepseek-ai/dsh-token-meter` 源码 + 本机真实会话日志，比夹具硬）：

- 投影单元的 **wire 视图**是 `view: (state) => state.totals`，而 **state** 才是 `{ totals, last }` —— 旧代码把 **state 形状**套在了 **wire 读面**上，两套词汇交叉；
- wire 的 schema 是 `.strict()` 的 `{ uncachedInputTokens, outputTokens, cacheReadTokens, cacheWriteTokens }`，恰好等于本模块白名单；
- **事件层**的 `TokenUsage` 是另一套词：`{ inputTokens, outputTokens, totalTokens }`（本机 `assistant/message` 实测，195 事件 / 618 处 `"usage"`）—— `totalTokens` 只存在于事件层，这多半就是"以为投影也有 totalTokens"的来源；
- 服务读法亦有第一方先例：`dsh-session-query` 用 `ctx.get('sessionProjections')?.snapshot(session)`，`dsh-api-session-controller` 用 `snapshot(agent.session, ['subagent']).values.subagent`。

## 9. 追加：`usage.get` 补真实耗时口径（`subagentTiming`），并堵掉"0 秒"陷阱

原实现把 `transcript_span_ms`（**会议发言的墙钟跨度**：该席两次发言相隔多久）摆在"耗时"位置，那是口径错配。第一方本来就有真东西 —— `@deepseek-ai/dsh-subagent` 的 `subagentTiming` 投影：`settledMs`（已结束回合累计毫秒）+ `active{since,through}`（当前未结束回合区间）。

- **新增字段** `agent_ms` / `agent_active`：`agent_ms = settledMs + (through - since)`，`agent_active = true` 表示数字来自**未结束**的回合；UI 显示 `~12.3s`（进行中）与 `12.3s`（已结算）区分，退回 transcript 时才显式标 `(transcript)`。
- **与 token 同一次快照**：`snapshot(session, ['tokenUsage','subagentTiming','subagent'])` 一次读三把钥匙，不为第二个指标重复物化；`test` 断言端点内 `snapshot(` 调用数**恒为 1**。
- ⚠ **实测陷阱（本轮最值钱的一条）**：`subagentTiming` 的 `init` 是 `{descriptorSeen:false, settledMs:0}`，而它的 wire 视图**只出 `{settledMs, active?}`** —— `descriptorSeen` 留在 state 里不上 wire。于是**没有描述符的会话**（例如主持人自己的顶层会话）也返回 `{settledMs:0}`，与"某个子代理所有回合都结算在 0ms"在 wire 上**同形**。直接采信会把跑了数小时的席位显示成 **0.0 秒**（实测：主持人会话读出 `agent_ms=0`）。判据用第一方的身份键：`subagent` 投影的 wire 值是 `SubagentIdentityProjection | null`，其文档明示 **`null` ⟺ 没有有效描述符**，故 `subagent === null/undefined` → 耗时**不可用**（`null`），不显示 0。
- **活会话实证（两个分支都真跑过）**：
  - 有描述符（现挂一个 12 秒探测子代理）：`live:true`、`provider_total:26126`、`agent_ms:3693`、`agent_active:true`；
  - 无描述符（主持人本会话）：`live:true`、`provider_total:252507781`、`agent_ms:**null**`（不是 0）；
  - 口径说明：`agent_ms` 的开放回合按**已折叠事件时间**计（`through` = 最新折叠进去的事件时间），长工具调用期间不跳表 —— **不是实时秒表**；这一条写进了 `src/usage.ts` 的模块文档，UI 侧以 `~` 标"回合进行中"。
- 新增 4 条夹具/护栏（含 `subagent:null` 必须为 `undefined` 的陷阱用例、以及"三钥匙同一次快照"的源码守卫）。
