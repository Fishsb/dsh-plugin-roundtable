# v0.2.57：预算 0 = 不限制 —— 一个取值，两个说法

**一句话**：用户要求「把会话轮次和上下文预算调到 0 表示不限制」。落点是 `max_rounds` / `max_tokens` 两条轴，但真正要修的不是"加个开关"，而是**同一个 `0` 在界面上有两套相反的含义**。

## 1. 缘起：界面说"0 = 不限制"，实现说"0 = 立刻停"

| 位置 | 改动前对 `0` 的说法 |
|---|---|
| 设置页输入框 | `min={1}` / `min={1000}`，且 `onChange` 里 `Math.max(1, …)` / `Math.max(1000, …)` |
| 专家限额那一栏的文案 | 「0 = 不限制（用模型默认）」（**同一页**） |
| `budgetExceeded` | `round >= maxRounds` ⇒ `0` 是**最严格**的上限：第 1 轮就 `0 >= 0` 立刻闭麦 |
| `plannedDefaults`（建会参数） | `>= 1` / `>= 1000` ⇒ 传 `0` 被**静默丢弃**并回落到 10 / 200000 |

三处三套语义。其中最坏的一档不是"0 立刻闭麦"，而是**参数被静默改写**：主持人按用户原话传了 `max_rounds: 0`，会议却按 10 轮建起来，且**没有任何信号** —— 用户的要求被无声换掉，事后无从察觉。这正是本仓反复在剿的「让失败不可观测」。

## 2. 修法：判据收敛成一个谓词，措辞收敛成两个渲染函数

```
src/budget.ts
  budgetUnlimited(limit)   // !(limit > 0) —— 唯一判定者
  budgetAxisText(max, used) // `N/∞` 或 `N/M`
  budgetLimitText(max)      // `∞` 或 `M`
```

- **判定者只能有一个**：`budgetExceeded` / 设置卡 / status / 导出 / 客户端预算条**全部**改走它，谁改口径都一起改。
- **`!(limit > 0)` 而不是 `limit <= 0`**：NaN 也归入"不限制"。NaN 参与比较恒假，若按"超限"处理会让闭麦**静默失灵**；按"不限制"处理则会议仍能收场。脏数据下选后果可控的一侧。
- **逐轴**语义：`maxRounds=0, maxTokens=100000` 是合法组合（轮数不限、token 仍管）。

参数接收改为 `parseBudgetArg`：缺省 ⇒ 回落；非负整数 ⇒ 接受（含 `0`）；**负数/非数 ⇒ 显式报错**（不静默回落 —— 上限为负几乎必然是笔误，静默回落会把笔误伪装成成功）。

## 3. 贯通六段链（逐处实测）

| 段 | 落点 | 不限制时的表现 |
|---|---|---|
| 核心判据 | `src/budget.ts` | 0 的轴 `budgetExceeded` 恒 `undefined`；两轴都 0 ⇒ 永不闭麦 |
| 参数接收 | `src/tools.ts` `plannedDefaults` / `set_budget` | `0` 被写入；负数报错；`set_budget` 解麦改用 `budgetExceeded` |
| 设置卡 | `src/plan.ts` | `0 轮（= 不限制：该轴永不闭麦）`（不再是"超限自动闭麦"） |
| status | `src/tools.ts` `renderStatus` | `Budget: 42/∞ rounds, 9999999/∞ tokens` |
| 导出物 | `src/tools.ts` `renderMeetingMarkdown` | `**预算用量**：42/∞ 轮 · 9999999/∞ token` |
| 设置页 / 拓扑条 | `RoundTableSettings.tsx` / `RoundTableView.tsx` | 输入框接受 0、给"不限制"提示；预算条显示 `N/∞` 且不画进度 |

`set_budget` 的解麦判据是**必须同批改的一处**：旧式 `fresh.round < fresh.budget.maxRounds` 在 `maxRounds=0` 时判成"仍在超限" ⇒ 补 0 反而**永远解不了麦**。

## 5. 顺手修掉的环境故障（与本次改动无关，但会挡住验证）

真机探针首次写入报 `atomic-write: timed out waiting for the writer lock at <profile>/package.json.lock`。**判因**：锁文件内容是 `3368`，该进程**已不在**；`dsh-atomic-write` 刻意**不会**自动清理既有锁（其源码注释：the contender never removes an existing lock），所以这条陈旧锁会永久挡住**任何**偏好写入。已核对该 PID 确已退出后删除锁文件，写入随之恢复。

**另一处（更要紧）**：部署链 `profiles/web/node_modules/dsh-plugin-roundtable` 曾**从 junction 退化成实体副本**（`fsutil reparsepoint query` 报 not a reparse point，字节比对 lib/index.js 不一致）。症状正是 `LOCAL-MAINTENANCE.md` §四.4 描述的那类：源码里明明有新代码、运行时却加载旧副本 —— **热重载也救不了**。已按该节步骤备份原目录（`.bak-entity-20260925-070019`）后重建 junction，字节比对通过，重载后端点回读新语义。

## 6. 边界（未做）

- **未**改默认值（仍是 10 轮 / 200000 token）：`0` 是**用户显式选择**的不限制，不是一个更宽松的缺省。改默认会替用户做决定，且与「越权面须拍板」相悖。
- **未**给不限制会议加"软提醒"之外的任何强制收场机制：不限制就是真的不限制，靠主持人判断与 `roundtable_close` 收场（`status` 仍每轮显示用量，看得见不等于被拦）。
- **未**动 `expertMaxTokens` / `expertMaxOpinions` 的 `0 = 不限制` 语义（它们本来就是对的，本轮只是把它们已坚持的口径推广到两条预算轴）。
- **未**把 `maxRounds` / `maxTokens` 的 Config 声明从 `z.natural()` 改掉 —— `natural()` 本就接受 0（实测 `s(0) === 0`，仅拒绝负数），负值由 `rpc.ts` 与 `parseBudgetArg` 两层拦下。
